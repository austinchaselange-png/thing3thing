# Things Cloud research notes

Reference studied: [wbopan/things-cloud-mcp](https://github.com/wbopan/things-cloud-mcp) at
commit `83135bb` (v1.4.3+), including its vendored fork of
[arthursoares/things-cloud-sdk](https://github.com/arthursoares/things-cloud-sdk).

Things Cloud has **no public API or documentation**. Everything below was
reverse-engineered by those projects from network captures of the official
Mac client. Cultured Code can change or block it at any time.

## What the MCP is

A Go server (≈4,600 lines in `main.go`) that exposes 23 MCP tools over
Streamable HTTP. It is multi-user: each request carries Things credentials
(HTTP Basic) or an OAuth bearer token minted by the server itself. The
maintainer runs a public hosted instance at `thingscloudmcp.com`.

### Capabilities (tools)

| Area | Tools |
|---|---|
| Read | `find_tasks`, `show_task`, `show_project`, `find_projects`, `find_headings`, `find_areas`, `find_tags`, `overview` |
| Create | `create_task`, `create_project`, `create_heading`, `create_area`, `create_tag`, `add_checklist_item` |
| Edit | `edit_item` (title, note, schedule, deadline, move, tags, reminder, recurrence, status incl. trash/restore), `edit_area`, `edit_tag`, `edit_checklist_item` |
| Delete (permanent) | `delete_area`, `delete_tag`, `delete_checklist_item` (all require `confirm=true`) |
| Debug | `debug_raw` (raw wire payload), `diagnose` (connectivity/integrity report) |

### Limitations observed

* Tasks are never permanently deleted; "delete" means trash (`tr=true`).
* Recurring tasks use a template + instance model. The MCP can create a
  template and first instance, but **new instances are generated by an official
  Things client** when it next syncs (iPhone in our case). Completing an
  instance does not generate the next one by itself.
* Reordering is limited to "insert at top" (`ix` below siblings' minimum).
* No push: the server is polled. Things Cloud enforces abuse prevention
  (`429` with `Things-Response: AbusePrevention`); the SDK rate-limits to
  1 request/second.
* Schema version is pinned at **301**. The SDK refuses reads and writes when
  the server reports a newer schema — this is correct fail-closed behaviour and
  we keep it.

## Protocol summary

Base URL `https://cloud.culturedcode.com`.

| Purpose | Request | Auth |
|---|---|---|
| Verify account, get history key | `GET /version/1/account/{email}` | `Authorization: Password {password}` |
| History head | `GET /version/1/history/{key}` → `latest-server-index`, `latest-schema-version` | history key in URL |
| Pull changes | `GET /version/1/history/{key}/items?start-index=N` → `items: [ {uuid: {t, e, p}} ]`, `current-item-index`, `schema` | history key in URL |
| Commit | `POST /version/1/history/{key}/commit?ancestor-index=N&_cnt=1`, body `{uuid: {t, e, p}}`, header `Schema: 301` → `server-head-index` | history key in URL |

* **Event-sourced.** Each outer array entry in `items` is one server index and
  may contain several entity events. `t` = action (0 create, 1 modify,
  2 delete), `e` = kind (`Task6`, `ChecklistItem3`, `Area3`, `Tag4`,
  `Tombstone2`, `Settings*`, plus legacy versions), `p` = partial payload.
  State is rebuilt by replaying events; a modify only sets the keys present,
  and an explicit `null` clears a field.
* **Identifiers** must be canonical Base58 (Bitcoin alphabet) encodings of 16
  random bytes. A malformed id written to the history crashes Things.app on
  every subsequent sync and permanently poisons the account (documented in the
  SDK's `client-side-bugs.md`). Legacy UUID-style ids are mapped with SHA-1.
* **Start state** `st`: 0 Inbox, 1 Anytime (Today when `sr`/`tir` is today),
  2 Someday (Upcoming when `sr` is set). `sb=1` = This Evening. Dates are
  date-only, stored as UTC-midnight epoch seconds.
* **Status** `ss`: 0 open, 2 canceled, 3 completed (`sp` = completion time).
* Tasks (`tp=0`), projects (`tp=1`) and headings (`tp=2`) are all `Task6`.
  Parent project `pr`, heading `agr`, area `ar`, tags `tg`. Headings must have
  `st=1`; `st=0` crashes Things.app. New items need a positive `ix`.
* Notes: `{"_t":"tx","t":1,"ch":crc32(text),"v":text}`; type 2 is a delta patch.
* `md` must be `null` on create; fractional epoch timestamps elsewhere.
* Reminders: `ato` = seconds after local midnight, `rmd` = reminder date.
* Recurrence `rr`: `fu` unit (16 daily, 256 weekly, 8 monthly, 4 yearly), `fa`
  interval, `of` detail list (`wd` weekday, `dy` day, `mo` month), `ia`/`sr`
  reference date, `ed` end date (`64092211200` = never), `rc` count, `tp` 0
  fixed schedule / 1 after completion.

## Authentication

* The account password is sent as `Authorization: Password <password>` only to
  the verify endpoint. It returns the **history key**.
* All history reads and commits are authorised **only by the history key in the
  URL path**. The SDK notes that `/items` does not require any other
  authentication. The history key is therefore a bearer secret that grants
  read *and write* access to the whole task database and must be protected
  like a password. It must never appear in logs, crash reports or URLs shown to
  the user.
* There is no OAuth, token expiry, scope or revocation that we know of.
  Changing the Things account password does not obviously rotate the history
  key.

## Security review of the MCP

Findings that drove our architecture:

1. **Hosted multi-tenant service.** Using the public endpoint means handing the
   Things password to a third party. Self-hosting still means the password
   lives on a server. → We embed a **local connector** in the desktop app; the
   password never leaves the PC except to `cloud.culturedcode.com`.
2. **A live credential is committed to the repository.** The MCP's
   `CLAUDE.md` contains a plaintext email + password for a test account and
   instructions to call the production server with it. We did not use it and do
   not reproduce it. It illustrates the risk this project must avoid: no
   credentials in the repo, build logs or CI environment.
3. **Debug logging dumps full requests and responses** (`THINGS_DEBUG`,
   `httputil.DumpRequest`) — including the `Authorization: Password` header and
   history-key URLs. → Our client has no request dumping; secrets are wrapped
   in a type whose `Debug`/`Display` is redacted, and URLs are logged with the
   history key masked.
4. **Client impersonation.** Requests carry `User-Agent: ThingsMac/32209501`,
   a fake `App-Instance-Id` and Mac device info. The server may depend on these
   headers; it may also use them to block clients. We keep the headers
   (behaviour parity with the tested SDK) but make them a single constant so
   they can be changed, and document this.
5. **MCP operations that are not safe for an unattended client:**
   * `delete_area`, `delete_tag`, `delete_checklist_item` — permanent
     (`t=2`). Deleting an area does not touch its tasks/projects, which can leave
     orphans. → Destructive operations sit behind a *second* opt-in, need typed
     confirmation, and we refuse to delete an area that still contains items.
   * `edit_item recurrence=none` trashes the template — permanent loss of the
     repeat rule. → Treated as destructive.
   * Recurrence creation/edit writes templates the official apps then expand —
     least-validated path. → Marked experimental in the UI.
   * `debug_raw`/`diagnose` — read-only but expose raw data and credentials
     paths. → Not ported.
6. **Good patterns worth keeping:** fail-closed schema checks; validating the
   whole page before advancing the cursor; `CommitUncertainError` with
   read-only reconciliation and **no automatic retry**; serialising all
   operations per account; client-side validation of every referenced id
   before writing.

## Conflict model (what the server gives us)

The commit carries `ancestor-index` (the last index the client has seen). The
SDK treats any `server-head-index` other than `ancestor + 1` as uncertain.
Whether the server rejects a stale ancestor, or accepts and appends, is **not
documented**; the reference code always pulls immediately before writing so the
window is small. Since every event is a partial field patch applied in order,
concurrent edits to *different* fields merge naturally, and edits to the *same*
field are last-writer-wins by server order. Our client adds field-level
conflict detection on top (see ARCHITECTURE.md).

## Risks of relying on the unofficial protocol

| Risk | Impact | Mitigation in Cairn |
|---|---|---|
| Protocol or schema changes | Reads/writes fail | Fail closed on schema > 301; app keeps working offline from cache in read-only mode |
| Malformed write | Things on iPhone crashes; account history poisoned permanently | Writes off by default; all payloads built by one tested module that mirrors the MCP's field-for-field; Base58 id validation before commit; headings forced to `st=1`; positive `ix` |
| Uncertain commit (timeout, dropped connection, 5xx) | Duplicate or lost write if retried | Never auto-retry; journal records the write before sending; reconcile by reading; block further writes until resolved |
| Account blocked for abuse / ToS | Sync stops | 1 req/s limit, polling ≥ 30 s, exponential back-off on 429 |
| History key leakage | Full read/write access to your tasks | Stored only in Windows Credential Manager, never in SQLite/logs |
| Recurrence semantics | Wrong next instance dates | Instances are generated by the iPhone app; Cairn displays them and only edits instances |
| Permanent deletes | Irreversible data loss | Second opt-in, typed confirmation, orphan checks, recommend a disposable account |
| No Mac backup available | Can't restore from Things for Mac backup | Recommend testing writes on a disposable account first; local cache keeps the raw event log as a forensic record (not a restore tool) |
