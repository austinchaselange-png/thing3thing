## Confirmed safeguards / coverage notes

- **Read-only policy:** engine.rs:297–314 enforces writes/destructive flags before any write or force-conflict override. Core::reapply_issue also checks writes (core.rs:575–581). “force” skips conflict checks only, not policy. Main can deliberately change policy via its authorized command. Permission-definition generation is excluded, so effective packaged ACL enforcement still needs validation. No fs/http/shell plugin grant appears in the inspected capabilities; networking and paths are mediated by Rust.
- Things Cloud verifies over HTTPS, removes URLs from reqwest errors (http.rs:44–51,113–114), uses redacted/zeroizing Secret (secret.rs:39–54), and stores passwords/history keys in OS Credential Manager with no plaintext fallback (credentials.rs:38–65). UI state excludes those secrets. Google credentials use distinct Credential Manager services (`drive.rs:21–22`, `gcal.rs:25–26`) and String fields rather than Secret; copies are not zeroized.
- Google uses loopback + state + PKCE (drive.rs:230–249; gcal.rs:299–316), drive.file and calendar.readonly plus identity scopes (drive.rs:23; gcal.rs:27). Calendar mutation commands are absent. Callback code validates state on successful code responses, but the error branch returns before checking state (drive.rs:532–537): a local unsolicited request can cancel sign-in. No token disclosure is implied.
- Both Google modules compile `TINGS3_GOOGLE_CLIENT_ID` and `TINGS3_GOOGLE_CLIENT_SECRET` into the binary when supplied (drive.rs:31–32; gcal.rs:33–34). Desktop installed-app client secrets are extractable and must never be treated as confidential-server credentials. Actual build environment and binaries were not inspected.
- SQLite uses WAL + synchronous FULL and transactions for events/cursor (cache.rs:103–106,151–174). Uncertain network commits are not blindly resent (engine.rs:357–371). Field revision conflict checks protect ordinary edits (318–328); unknown format blocks writes. Offline edits are not a durable queue: pre-sync failure rejects them, and store.ts:315–318 removes the optimistic pending edit and reports an error.
- Input enums, entity existence, IDs, dates, reorder/delete limits are checked (mutation.rs:267–275,342–349,650,686; ops.rs:24–29). Text/checklist/network response budgets are incomplete (ops.rs:73–86; mutation.rs:413–417; http.rs:121; drive.rs:435). No generic arbitrary local-file path command was found. Download names strip path separators but files are directly overwritten (commands.rs:206–208).
- CSP uses self scripts and IPC-only connect-src (tauri.conf.json:16). No release devtools enablement was seen in shell.rs. React text paths are escaped by JSX; no dangerouslySetInnerHTML appeared in the permitted components. The actual Markdown renderer, links handling and calendar UI are outside scope, so XSS/deep-link safety there is **not certified**.
- Date-only wire values use UTC midnight as an encoding, UI day arithmetic uses local calendar components (dates.rs:7–16; src/lib/dates.ts:4–28). Rounded local day differences tolerate ordinary DST changes. Calendar cache uses one-day overlap slack for all-day events (gcal.rs:175–191). Runtime timezone/leap-day/recurrence behavior was not executed.
- Logs include error strings, policy choices and possible panic text (core.rs:194,411,562). Journal summaries include task titles (mutation.rs:419,544–546) and are persisted and sent to the UI (cache.rs:187–190; core.rs:267). This is personal data in an unencrypted local SQLite cache, not leaked credentials. No persistent logger setup/rotation was established from lib.rs; actual log destination and crash output are unverified.

## Cross-program pass and final manifest check

The Calendar merge/error paths match Chrono C-S06: Things `gcal.rs:550–581` and Chrono `gcal.rs:612–641`. Things already projects event fields (`gcal.rs:590–594`), which Chrono can adopt, but its silent ten-page cap must not be copied. Both need bounded workers, shared clients and account-generation checks. Chrono Drive already reuses its HTTP client and serializes sync runs; Things lacks that operation lock (T-S04), while neither remote replacement protocol protects against competing devices. T-S01 applies specifically to PC-local/Demo mode (`core.rs:675`), not direct replacement of Things Cloud's server history.

Supplemental X-S01 (Low, confidence high; ranked in AUDIT-SUMMARY.md): the shared Things OAuth callback (`drive.rs:532–537`, used by Calendar) accepts error responses before validating state; Chrono Calendar copied this (`gcal.rs:184–189`). A local unsolicited callback can cancel sign-in, without stealing tokens. Check state for error as well as success responses. Chrono Drive already checks it first (`drive.rs:370–377`).

The spelling TINGS3 is consistent in both Things Google modules and aligns with the `tings3` package / `app.tings3.desktop` identifier; it is not a demonstrated typo. A build setting only THINGS3_* would fail to populate the optional constants, so verify the actual build configuration later. Chrono uses adjacent-file/user configuration instead, not these variables. Credentials are in distinct service/account entries; no automatic cross-app token sharing was found. Installed desktop client secrets are extractable whether compiled or shipped in a JSON resource. Phase 5 rechecked declared dependencies; exact resolution, CI, ignore rules and release evidence remain outside scope.

## Invariants the app relies on

The global write policy remains enforced in every mutation path; the cache belongs to one account/history; Sending entries are eventually reconciled; mutations cannot outlive an account switch; restore preserves old bytes before replacement; a calendar range is replaced only when completely fetched; all windows granted mutation authority are equally trusted. Several findings arise from these assumptions being broader than enforcement.
